# Phase 6.5 - 真实产物驱动的全链路调优与仓库拆分调研

## 阶段状态

筹划中。

## 定位

Phase 6 已经证明系统可以生成、Judge、保存并导出真实 PoB / `.build`。在进入 Phase 7 深度
Critic 修复循环前，先利用这些真实产物校正 Phase 1-5 和公共工具链，避免后续循环放大已有
评分偏差、知识缺口或不真实配装。

本阶段同时调研把 Exile Architect 从 `MaxWilk/poe2-build-mcp` 的派生仓库历史和完整应用代码中
拆出。目标不是否认或隐藏上游，而是把其 MIT 许可的 PoE2 MCP / Headless PoB 基座变成明确、
可追踪、可替换的外部依赖，让 Exile Architect 成为拥有独立历史、命名和发布边界的新项目。

## 工作流

```text
固定真实 BuildBrief
  -> Agent 生成并导出 PoB / .build
  -> 人工与工具审计真实可玩性
  -> 把问题按 Judge / Research / Compute / Generation / Export 归因
  -> 修正对应前置环节
  -> 重跑同一请求和回归样例
  -> 只有可测改善才保留
```

Phase 6 继续作为验收探针，不因前置阶段被修正而重新进入“进行中”。

## O6.5.1 固定真实样例集

建立一组规模不大但覆盖面明确的固定请求与产物审计表：

- 开荒法术、攻击、召唤各至少一个；
- 进图或攻坚至少一个；
- 至少一个多技能协同、条件触发或 PoB 部分可建模候选；
- 普通模式和 `--no-memory` 使用同一道题；
- 每个样例保留安全运行元数据、Judge 报告、完整度报告和本地 artifact 引用，不把 PoB 原文写入
  Git。

人工审计维度至少包括：

- 技能职责与实际轮转；
- 黄装、暗金、底材等级、词缀和预算真实性；
- 符文/灵魂核心、天赋珠宝、药剂和护符；
- 天赋路径与点数使用；
- 资源、Spirit、恢复和防御层；
- 清图、Boss 和目标阶段适配；
- PoB/Judge 结论与人工判断的差异。

验收：同一套样例能重复生成结构化问题清单，并能判断修复前后是否真的改善。

## O6.5.2 Judge 调优

重点不是提高平均分，而是提高“分数和实际 BD 质量的一致性”：

- 把硬合法性、阶段完整度、数值质量和 modelability evidence 继续分层；
- 使用多技能职责描述，避免把条件爆炸、战旗、辅助伤害层或单个面板误当整个 BD；
- 对清图、Boss、持续输出、资源恢复和机动性形成最小分场景证据；
- 检查当前评分是否过度奖励抗性、EHP、占位装备或理想化黄装；
- 对药剂、护符、珠宝、符文和装备预算提供诊断，但不把 Agent 设计变成固定模板；
- Judge 与人工判断冲突时记录可复现案例，优先修证据合同，不用新增主观权重掩盖问题。

验收：固定样例中的误通过、误失败、错误主输出识别和明显评分排序错误减少；已有合法性回归不退化。

## O6.5.3 Phase 4 知识提取调优

使用 Phase 5/6 真实失败证明 Agent 实际缺少什么知识，再调整 Researcher extraction：

- 强化技能组合、职责、轮转、触发与伤害兑现关系；
- 提取装备角色、黄装词缀组合、底材/物品等级、符文、珠宝、药剂和护符信息；
- 区分开荒、进图、攻坚、终局的预算与可获得性；
- 提取“为什么这样配”以及不满足前提时的失败模式，而不是只记录共同出现；
- 记录 PoB/Judge 可建模性边界和人工验证需求；
- 审计现有 memory 检索是否返回足够具体、可执行且不过度宽泛的经验。

验收：memory-assisted 固定请求在机制完整度、装备真实性和首次 Judge/人工通过率上优于
`--no-memory`；提升必须能追溯到实际使用的 fragment / pattern / edge。

## O6.5.4 Compute 与 Agent 工具调优

- 完善阶段化黄装、底材、词缀、符文/灵魂核心、珠宝、药剂和护符工具；
- 区分中途计算 scaffold 与最终可玩装备；
- 让工具返回可审查候选和证据，不替 Agent 自动决定完整 BD；
- 收集工具误判、空结果、状态污染、过慢调用和难以发现的工具入口；
- 检查 skill 是否把关键工具、调用顺序和停止条件表达清楚。

验收：固定请求不再依赖占位装通过 Judge，最终 artifact 的真实装备系统完整度提高，工具调用失败率
和无效重复调用减少。

## O6.5.5 仓库拆分可行性

### 当前事实

- 当前 Git 历史以 `MaxWilk/poe2-build-mcp` 为祖先，保留上游 MIT License；
- 上游是完整 MCP 应用，`pyproject.toml` 使用 `package = false`，不是可直接安装的稳定 Python 库；
- Exile Architect 直接依赖并修改了 `server.compute`、`pob/pob_headless.lua`、corpus、live/update、
  MCP 注册和打包流程；
- 因此只删除 `upstream` remote 或修改仓库名，不能实现真正的外部依赖化。

### 候选路径

1. 新建干净 Exile Architect 仓库，依赖一个固定版本的外部 PoE2 runtime MCP 服务。
   - 优点：产品边界最清楚，Agent 通过 MCP 合同访问底层；
   - 风险：当前需要的自定义 PoB bridge、工具和数据能力必须先由 runtime 提供；跨服务状态、安装和
     版本管理需要重新设计。
2. 新建干净仓库，把必要上游代码整理成独立的 `exile-runtime` 包或独立仓库，再由主项目依赖。
   - 优点：可保留 Python 级调用和完整测试能力，长期边界最稳定；
   - 风险：需要维护一个明确的 runtime fork、发布包和兼容矩阵，工作量最大。
3. 新建干净仓库，通过 Git submodule/subtree 固定上游或 runtime fork。
   - 优点：迁移较快、来源清晰；
   - 风险：并没有形成真正稳定 API，主项目仍容易直接 import 内部实现，升级和打包复杂。

### 初步建议

优先调查“路径 2，最终可兼容路径 1”：

- 把 Headless PoB、PoB code codec、静态 corpus 和必要计算工具定义成独立 runtime 合同；
- Exile Architect 只保留 Judge、graph/memory、Researcher/Architect contracts、generation、artifact、
  converter 和产品 skill；
- runtime 可以先作为固定版本的本地包/独立仓库使用，成熟后同时暴露 MCP 服务；
- 新仓库保留上游 MIT attribution 和改动说明，但使用新的独立 Git 历史；
- 在接口和双仓验证完成前，不删除当前仓库或中断现有可运行版本。

### 调研产物

- 文件和模块归属清单：保留在主项目、迁到 runtime、替换为外部服务或废弃；
- 主项目到 runtime 的最小接口草案；
- PoB 状态所有权、并发、版本、安装、更新、打包和测试策略；
- 许可证与 NOTICE 方案；
- 双仓迁移步骤、回滚方案和工作量估算；
- 一个只验证 `new_build -> set_skill -> Judge -> artifact export` 的跨边界 spike。

验收：在不复制整个旧应用到新仓库的前提下，spike 可以通过稳定接口完成最小闭环；否则不开始正式
迁移。

## 顺序建议

1. 先建立固定真实样例和问题分类；
2. 优先修 Judge 与装备/技能完整度的高影响误判；
3. 用失败样例反推 Phase 4 extraction 和 memory 检索；
4. 并行完成仓库拆分接口调研和最小 spike；
5. 人工确认调优结果和拆分路径后，再决定是否新建两个仓库；
6. 调优稳定后进入 Phase 7，避免 Critic loop 放大未校正的评价器和工具偏差。

## 非目标

- 本阶段不实现 Phase 7 自动 Critic loop；
- 不把一次 Judge 分数提高视为调优成功；
- 不直接删除当前仓库历史或上游 attribution；
- 不在没有稳定接口和迁移回滚方案时创建半成品双仓结构；
- 不把底层 runtime 的工具选择权变成程序化 BD 自动补全。

## 进度维护

- 本文只维护本轮跨阶段调优和拆分调研；原 Phase 文档继续维护各自长期合同；
- 每个完成且有验收证据的工作项后标记“已完成”；
- 复杂迁移方案必须先呈现给用户确认，不默认选择降级路径。
