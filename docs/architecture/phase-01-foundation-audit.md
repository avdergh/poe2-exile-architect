# 第一阶段：Fork 基线与版本可信度审计

## 目标

第一阶段建立一个可重复验证的上游基线，并加入最小但严格的数据新鲜度门禁。完成后，系统必须能回答：

1. 当前运行的游戏补丁、挑战联盟和天赋树版本是什么；
2. 本地 PoB 引擎、PoB 数据、语料库和 Meta 快照分别来自哪个版本；
3. 这些版本是否足以把构筑标记为 `verified_current`；
4. 若不能验证，具体是哪一层落后、冲突或不可用。

这一阶段不实现构筑生成、长期记忆或多 Agent 搜索。它只建立后续所有模块共同依赖的可信底座。

## 上游选择

代码基线采用 `MaxWilk/poe2-build-mcp`：

- 许可证：MIT；
- 已具备无头 PoB、MCP、SQLite 语料和基本优化接口；
- 代码与数据更新可分离；
- 现有实现缺少完整的跨来源版本一致性判定，正是本阶段的改造重点。

其他项目的处理原则：

- GPL 项目只用于能力调研，不复制实现；
- 无许可证项目只研究公开协议行为，相关适配器独立重写；
- 所有引入代码必须记录来源和许可证。

## 当前问题

上游的 `check_data_version` 主要比较 RePoE 文件时间，并返回当前联盟名称。这不足以证明：

- PoB 引擎支持当前游戏补丁；
- PoB 的天赋树与 Ninja 快照使用同一树版本；
- 暗金、宝石和词缀数据属于当前赛季；
- 当前补丁是否包含会影响构筑计算的变更。

因此，“语料库刚更新”不能等价于“当前赛季构筑已验证”。

## 版本清单

新增统一的 `FreshnessManifest`，至少包含：

| 组件 | 必要字段 |
|---|---|
| 游戏 | 补丁号、发布日期、来源 URL、抓取时间 |
| 联盟 | 名称、Ninja slug、快照版本、样本时间 |
| 官方天赋树 | 树版本、来源提交或快照标识 |
| PoB 引擎 | PoB 版本、提交、支持树版本 |
| PoB 数据 | 技能、暗金、宝石数据提交 |
| RePoE | 数据更新时间或内容摘要 |
| Wiki | 查询时间与页面 revision（按实体记录） |

版本清单必须保存原始来源信息，不能只保存一个合并后的“最新”字符串。

## 新鲜度状态

系统对每个来源先独立分类：

- `current`：与当前游戏/联盟版本一致；
- `stale`：明确落后；
- `conflicted`：两个可信来源给出不兼容信息；
- `unknown`：无法确认或来源不可用。

整体门禁再输出：

- `verified_current`：所有强制组件均为 `current` 且版本兼容；
- `current_unmodelled`：数据属于当前版本，但 PoB 明确不能完整计算关键机制；
- `blocked_stale`：至少一个强制组件落后；
- `blocked_conflict`：存在版本冲突；
- `blocked_unknown`：缺少强制证据。

门禁采用保守策略：无法证明为当前版本时，不得自动升级为 `verified_current`。

## 组件边界

第一阶段新增以下模块：

- `server/freshness/models.py`
  - 定义不可变的来源状态、组件记录和整体报告。
- `server/freshness/evaluator.py`
  - 只负责纯函数版本兼容性判断，不执行网络请求。
- `server/freshness/providers.py`
  - 后续承载 GGG、PoB、Ninja、RePoE 等来源读取；第一切片先提供本地/静态输入接口。
- `server/freshness/service.py`
  - 聚合来源并生成报告，供 MCP 和 CLI 使用。

将网络抓取和判断逻辑分开，使测试不依赖实时网站，也便于保存 fixture。

## 注释规范

关键注释解释以下内容：

- 为什么某个来源是强制门禁；
- 为什么某些版本可以兼容或必须阻断；
- 为什么选择保守降级而不是猜测；
- 第三方接口中不直观的字段含义。

不添加逐行翻译代码行为的注释。

## 测试策略

测试遵循 TDD：

1. 当前游戏、树、PoB 与联盟快照一致时，报告为 `verified_current`；
2. PoB 提交落后且未声明兼容时，报告为 `blocked_stale`；
3. Ninja 树版本与官方树冲突时，报告为 `blocked_conflict`；
4. 缺少游戏补丁证据时，报告为 `blocked_unknown`；
5. 数据当前但关键机制未建模时，报告为 `current_unmodelled`；
6. 报告必须列出阻断原因，不能只返回布尔值。

网络 provider 的测试使用保存的 fixture；纯 evaluator 测试不使用 mock 网络。

## 第一阶段完成标准

- 上游测试可在本机运行，或明确记录缺失运行时；
- 新鲜度 evaluator 的测试经历红—绿循环并全部通过；
- MCP 暴露结构化新鲜度报告；
- 现有 `check_data_version` 不再把单一 RePoE 时间当作全局验证；
- 文档记录本地基线、上游版本和仍未解决的能力缺口。
