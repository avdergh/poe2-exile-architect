# 新鲜度门禁

## 职责

新鲜度门禁回答一个问题：**当前证据是否足以把研究结果标记为当前赛季已验证？**

它不负责下载数据，也不判断某个 BD 强不强。网络 provider 把外部响应转换为统一证据，
门禁对这些证据做纯函数判定。

## 证据模型

每条 `FreshnessEvidence` 记录：

- 组件：游戏补丁、联盟、官方天赋树、PoB 引擎、PoB 数据、语料库或 Meta 快照；
- 来源名称、来源 URL 和观察时间；
- 来源自身状态：`current`、`stale`、`conflicted`、`unknown`；
- 来源版本；
- 兼容性声明，例如 `game_patch=0.5.3`、`passive_tree=0_5`。

兼容性声明用于跨来源核对。PoB、官方树和 Ninja 即使各自都声称“当前”，只要它们声明的
`passive_tree` 不一致，整体仍必须阻断。

兼容性维度是封闭枚举：`game_patch`、`league`、`passive_tree`。每个强制组件都有最小
声明覆盖要求；只有 `status=current` 和非空版本、却缺少必要声明时，仍属于
`blocked_unknown`。空的强制组件集合是非法输入，不能通过调用方配置绕开安全基线。
联盟 claim 使用统一 slug 形式，因此官方名称 `Runes of Aldur` 与
`runes-of-aldur` 被视为同一联盟。

同一来源对同一组件可能保留历史记录。判定前只选择 `observed_at` 最新的一条作为活动
证据，避免旧快照污染当前结论；如果并列最新记录内容不一致，则直接视为来源冲突。
不同来源的当前证据仍会相互核对。

报告同时保留 `evidence`（完整审计输入）和 `active_evidence`（本次裁决使用的最新证据）。
状态为 `unknown` 的来源不参与版本冲突比较，因为它没有资格提供已知事实，但仍会产生
未知阻断。非强制来源的并列记录只生成警告，不能撤销当前判定。

## 强制组件

默认强制组件：

1. 游戏补丁；
2. 当前联盟；
3. 官方天赋树；
4. PoB 引擎；
5. PoB 数据；
6. 本地语料库；
7. Meta 快照。

Wiki 等长尾来源可以作为非强制证据。缺少强制组件时，不允许用其他来源推测补齐。

## 判定优先级

从高到低：

1. `blocked_conflict`：显式冲突，或跨来源兼容性声明不一致；
2. `blocked_stale`：至少一个强制组件明确落后；
3. `blocked_unknown`：强制组件缺失或状态未知；
4. `current_unmodelled`：版本一致，但存在 PoB 无法建模的关键机制；
5. `verified_current`：所有强制证据为当前、兼容且关键机制可建模。

冲突优先于过期，因为“已知两个答案不一致”比“已知一个来源落后”更需要停止自动研究。
判定优先级只决定顶层状态；报告仍要列出同一批证据中的冲突、过期和缺失声明等全部
阻断原因。

## 输出

`FreshnessReport` 必须包含：

- 整体判定；
- 原始证据；
- 可供用户和 Agent 阅读的阻断原因；
- 非阻断警告；
- 判定时间。

不能只返回 `true/false`。后续 BD 报告必须能解释自己为什么没有“当前已验证”标签。

## 测试边界

判定器测试不访问网络，不 mock HTTP。至少覆盖：

- 全部一致；
- PoB 过期；
- Ninja 与官方树冲突；
- 缺少官方补丁；
- 当前版本但关键机制未建模；
- 非强制来源过期不阻断。
