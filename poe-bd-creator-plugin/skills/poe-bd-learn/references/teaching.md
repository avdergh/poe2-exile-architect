# 把研究结果组织成学习文档

读者要知道这个 BD 怎么运转、每个选择解决什么问题，以及上手时怎样观察。Research 的记录结构
用于保证分析完整；Learning 的阅读顺序围绕读者需要先理解什么来安排。

## 阅读路线

通常先让读者认出主输出、准备动作和维持条件，用一张短流程图串起来；随后解释操作、伤害放大、
技能和装备为何配套，再看天赋与升华、资源和防御。根据具体 BD 调整顺序，不固定十个可见标题。
先出现的术语用一句话解释，再展开复杂联动；同一机制后文通过简短引用连接，避免反复从头讲。

小标题说明读完这一节能理解什么，例如“先建立旋风再投出 Twister”“两套武器如何分工”
“投射物速度为何值得投资”。不要用内部分类名充当所有标题，也不要刻意把标题都写成问句。
正文保持具体、连贯，解释原因之后再给条件或取舍，避免所有组件套用同样的卡片句式。

## 把限制讲成有用的知识

不能删掉真实限制或把未知改成确定，也不应让读者阅读一份工具执行反馈。

- 内部记录：“Spirit 请求超过容量，不能认证所有增益同时启用。”
  学习表达：“安排常驻技能时要看总 Spirit 占用。这份导入的启用组合超过了容量，因此实装时先
  核对武器切换和启用列表，不能照着所有勾选同时开启。”放在资源安排章节，并保留必要数值。
- 内部记录：“辅助有 application receipt，但没有直接收益证据。”
  学习表达：“这颗辅助需要技能先造成破甲；当前宿主没有明显的破甲事件，所以不能把它算作这一组
  的稳定破甲来源。若它承担颜色配置职责，应另看升华条件。”放在对应技能旁，不能编造作者动机。
- 内部记录：“面板不是完整总 DPS。”
  学习表达：“旋风数量增加不代表 Boss 受到的伤害按相同倍数增加，还要看命中间隔与接触时间。”
  放在输出机制。只有数值能帮助读者理解时才引用面板，并说明它表示什么。

不统一追加“哪些结论尚未验证”审计清单。需要版本说明或测量方法时使用简短附注；会影响技能、
资源、操作选择的限制仍应在正文就近出现。对可疑配置如实解释，不以“看似无用其实很巧妙”强行合理化。

## 让文档便于学习

主产物使用连续阅读的 H5 学习页。章节导航、搜索、组件类别和按需说明帮助读者找信息；页面保留
完整正文，不依赖 PDF 分页，也不恢复此前的天赋树或脱离正文的联动展示。

不要默认读者知道英文名称属于什么。先区分技能、辅助、装备随机名、底材、天赋、符文和属性。
装备、天赋与符文使用各自的真实图标，点开名称可以看类别和说明；属性或场上效果用概念说明。
例如 Loath Ward 是随机装备名、Slipstrike Vest 是胸甲底材、Beastial Skin 是天赋，Deflection
在该段落是防御属性。这些身份需要直接讲清，不让读者从图标有没有出现来猜。

- 流程图表现真实先后或依赖关系，不用箭头把无关组件串在一起，不画未经测量的数值模拟。
- 表格用于两套武器、辅助职责、属性取舍等横向比较；长机制解释保留段落，不能把整本攻略塞进表格。
- 随文提示用于一个容易混淆的概念或一个可观察动作，例如“地面强化与敌人异常不是同一条件”。
- 每件装备、每颗宝石和关键天赋都要讲，但可在读者已有上下文时紧凑表达。不要为了好看削减提取深度。
- 上手建议应是可观察的小步骤，如先看准备对象是否被消耗，再加入充能技能；不要虚构学习评分、
  承诺几分钟掌握，也不要安排没有本 BD 依据的任务。
- 首先跟随用户本次请求的语言，明确指定其他语言才覆盖；英文游戏名不改变正文语言。使用已核实
  官方名称，未确认时保留英文名，周围说明仍使用用户语言。图表标题、提示和导读也不能混用另一语言。
- 每处具体组件名后统一插入身份绑定图标。标题与正文使用同一个名称渲染器，不靠手工逐项贴图。
  同名状态用 term token 表明职责；追加的比较技能和授予技能用 iconSkillRefs 绑定精确身份。

提交 guide 前，Agent 检查阅读路线、细节保留、限制是否就近解释、图表是否帮助理解。结构校验只查
覆盖和引用，不能以字数、禁词列表或布尔声明代替真实的教学编辑。
