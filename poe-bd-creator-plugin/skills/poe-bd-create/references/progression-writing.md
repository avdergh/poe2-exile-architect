# Progression 成长指南写作

只在完整 progression 中使用。目标是把已经验证的阶段数据讲成玩家能照着玩的教学指南，
不是把内部 schema、Research 记录或 Judge 字段换成 Markdown。

## 每个阶段怎么写

完成 `StageCompletionReport` 时，保留原有字段，并尽量填写 `playerGuide`：

```json
{
  "mechanicExplanation": "这一阶段为什么选这些技能，它们各自负责什么，以及伤害或资源怎样运转。",
  "levelingSteps": [
    "从上一里程碑开始，先取得什么技能或装备，暂时继续用什么。",
    "中途解锁什么后加入哪个功能，为什么此时加入。",
    "到达本阶段等级时检查什么，满足后才算完成。"
  ],
  "commonProblems": [
    {
      "symptom": "玩家在游戏里能直接观察到的现象。",
      "solution": "先检查什么，再怎样调整；不要只写‘继续优化’。"
    }
  ]
}
```

- `purpose`：说明玩家在这一阶段要完成什么，以及为什么现在做。
- `playPattern`：用口语分别讲清普通怪、稀有怪和 Boss 怎么按技能；不适用的场景可以省略。
- `mechanicExplanation`：从零解释技能之间的因果关系。英文技能第一次出现时，顺手说明它的职责，
  例如“Tempest Bell（放钟，负责 Boss 爆发）”。如果阶段使用精魂/保留技能，还要说明它消耗的
  Spirit、提供的增益和为什么与主技能搭配；不使用时说明这一阶段采用了什么替代方案。
- `levelingSteps`：写从上一阶段到当前等级之间的成长过程，不要只描述当前快照。第一阶段必须从
  建号开始；后续阶段重点写新增、替换和保留的内容，以及为什么此时改变。
- `acquisitionPriorities`：按技能、武器/装备、天赋和资源的实际先后顺序写；避免数据库式标签。
- `commonProblems`：写玩家能看见的症状与可执行处理办法。没有可靠答案时明确说需要实战确认。
- `caveats`：只放影响游玩的注意事项，不放内部证据状态、Family key、artifact id 或枚举。
- `transitionReadiness`：写成玩家可以逐项核对的转型清单；价格只能提示风险，不能代替机制条件。

## 文风

- 先讲目的，再讲原理，然后讲操作和升级步骤；用“因为……所以……”说明取舍。
- 假设读者第一次接触这个流派。不要直接使用“Family、闭环、兑现、窗口、bootstrap、modelability”
  等内部或抽象词；确实需要术语时先用一句人话解释。
- 不照抄 Research 标题、record kind、typed payload 或 Judge 文本。把证据转成玩家行为，再保留安全
  引用供技术附录复核。
- 不编造掉落等级、任务奖励、数值或机制。没有验证的内容用“建议”“预计”或“需要实战确认”。
- 教学要具体，但每段只解决一个问题；不要写成长篇背景故事或重复列完整装备、天赋和技能镜像。

## 提交前自查

- 玩家是否知道这一阶段为什么这样搭配、平时怎么打、Boss 怎么打？
- 玩家是否知道精魂/保留技能什么时候加入、帮助了什么，或者为什么本阶段不用？
- 第一阶段是否真的覆盖建号到第一个里程碑，而不只是一个等级快照？
- 后续阶段是否说清改了什么、为什么现在改、没满足条件时继续用什么？
- 每个常见问题是否包含可观察症状和处理办法？
- 删除内部 ID 和枚举后，正文是否仍然完整可读？
